# Hermes Orchestration Contracts

**Status:** Current — validated via pkb-trial-001 and session-1 delegation cycles (control-record verification, technical analysis, portfolio documentation updates).
**Scope:** Read-only planning, supervised packet creation, delegation, verification, and restart continuity. Proven via pkb-trial-001 (control-record verification), pkb-footprint-review (technical analysis), and session-1 portfolio documentation updates.

## User Intent

Owned by `schemas/hermes_orchestration/user-intent.schema.json`.

Minimum fields:
- `intent_id`
- `objective`
- `repositories`
- `authority_envelope.permitted`
- `authority_envelope.prohibited`
- `authority_envelope.requires_buddy_approval`
- `duration_bound`
- `scope_boundary`
- `stop_conditions`

The user-intent artifact constrains roadmap selection, packet generation,
dispatch authority, continuation, and stop behavior. It is run-specific and
must not be stored in Hermes memory.

## Repository Context

Owned by `schemas/hermes_orchestration/repository-context.schema.json` and
generated by:

```bash
python3 -m tools.hermes_orchestrator context --repo <path> --slug <slug>
```

Minimum fields:
- repository identity and path
- branch and HEAD
- remotes and divergence
- status, worktrees, stash
- classified dirty/untracked state
- control record digest when available
- lock state
- stop reasons

Dirty or untracked state locks mutation. Read-only planning may continue when
the intent permits it.

## Repository Intake

Repository intake is the safe entry mode for pointing Hermes at one managed
repository before planning or implementation. It is read-only and owned by
`schemas/hermes_orchestration/repository-intake.schema.json`.

```bash
python3 -m tools.hermes_orchestrator intake-repository \
  --repo <managed-repo-slug> \
  --path <checkout-path> \
  --task-id <stable-intake-task-id> \
  --archive-root _internal/orchestration
```

At least one of `--repo` or `--path` is required. When `--archive-root` is
provided, `--task-id` is required so the intake report can be placed in the
repository-organized durable artifact tree:

```text
_internal/orchestration/repos/<repo>/tasks/<task-id>/
  intake.json
  intake-report.md
  manifest.json
```

Intake records:

- repository identity and control-record match;
- Hermes scope declared in `repos/<repo>/CONTROL.md`;
- branch, HEAD, remotes, divergence, and dirty/staged/unstaged/untracked state;
- whether observed changes appear pre-existing;
- presence and evidence status of `CONTROL.md`, `ROADMAP.md`, `TODO.md`,
  `README.md`, internal README variants, `AGENTS.md`, and operational docs;
- roadmap and TODO status without promoting either above unresolved authority;
- unresolved human decisions and obvious blockers;
- suitability for read-only analysis, bounded documentation work, delegated
  implementation, and VPS onboarding/deployment work;
- recommended next bounded tasks, missing evidence, and contradictions.

Statuses:

- `INTAKE_COMPLETE` — control record and path identity are sufficient for
  read-only intake.
- `AUTHORITY_UNRESOLVED` — no active control-plane control record or required
  archive/task identity is missing.
- `IDENTITY_CONFLICT` — supplied slug/path conflicts with the control record.
- `RESTRICTED` — the control record declares Hermes scope `none`.

`AUTHORITY_UNRESOLVED`, `IDENTITY_CONFLICT`, and `RESTRICTED` are fail-closed
statuses. Hermes must not use an intake result with those statuses to plan,
delegate, or authorize implementation. A dirty tree is evidence to protect and
classify; it is not a reason to skip read-only intake and is not permission to
repair, stage, clean, or overwrite untracked files.

## Authority Resolution

Authority resolution is mandatory before repository ranking or task planning.
It is owned by
`schemas/hermes_orchestration/authority-resolution.schema.json` and generated
by:

```bash
python3 -m tools.hermes_orchestrator authority-resolve \
  --candidate ivy-control-vps=/Users/buddy/projects/ivy-control-vps \
  --candidate ivy-control=/Users/buddy/projects/ivy-control
```

The resolver inspects root authority documents in each plausible control-plane
candidate:

- `AGENTS.md`
- `README.md`
- `ROADMAP.md`
- `registry/repos.yaml` when present

It records candidate control planes, documents checked, authority claims,
delegation or redirect evidence, registry taxonomy policy, conflict status,
resolution, confidence, and whether it is sufficient to continue.

Registry classification and ecosystem membership are inventory, not governance
authority. A registry entry cannot be the sole basis for one control plane to
govern another. Explicit redirect or delegation evidence is required before one
control plane governs another. If multiple control-plane claims remain
unresolved, Hermes must stop with `AUTHORITY_CONFLICT`. If no explicit
authority claim exists, Hermes must stop with
`AUTHORITY_INSUFFICIENT_EVIDENCE`.

Valid statuses:

- `AUTHORITY_RESOLVED`
- `AUTHORITY_CONFLICT`
- `AUTHORITY_INSUFFICIENT_EVIDENCE`

## Roadmap View

Generated by:

```bash
python3 -m tools.hermes_orchestrator roadmap --roadmap <path>
```

The parser recognizes approved package headings such as
`### PKB-FL-01 — Repository State Reconciliation and Publication Gate` and
extracts outcome, dependencies, validation, gates, included/excluded work, stop
conditions, and completion criteria. The parsed view is derived evidence; the
roadmap file remains authority.

## Eligibility and Selection

Repository selection and executor selection are separate decisions. Hermes first
evaluates repository candidates and recommends the highest-priority eligible
repository. Only after a repository and task are approved does Hermes route the
work to an executor.

The control-plane repository `ivy-control-vps` participates in candidate
evaluation unless governance or user intent explicitly excludes it. Delegation
does not imply leaving the control-plane repository; it means Hermes
coordinates while a separate execution agent performs bounded implementation.

Repository recommendation is generated by:

```bash
python3 -m tools.hermes_orchestrator rank-repositories \
  --intent <intent.json> \
  --authority-resolution <authority-resolution.json> \
  --context <repo-context.json> \
  --context <another-repo-context.json>
```

The recommendation output records every candidate, eligibility, priority score,
reasons, and `executor_selection: not evaluated here`.

Generated by:

```bash
python3 -m tools.hermes_orchestrator plan \
  --intent <intent.json> \
  --authority-resolution <authority-resolution.json> \
  --context <context.json> \
  --roadmap <roadmap.json> \
  --out-dir <proof-dir>
```

Selection is deterministic: roadmap order after dependency and envelope
filtering. The output records the selected task and the exclusion reason for
every non-selected task.

Before human approval, use dry-run planning:

```bash
python3 -m tools.hermes_orchestrator plan \
  --intent <intent.json> \
  --authority-resolution <authority-resolution.json> \
  --context <context.json> \
  --roadmap <roadmap.json> \
  --dry-run
```

Dry-run planning returns a draft packet and writes no files. New active run
directories, target-repository task packets, and durable task artifacts are
created only after explicit approval unless repository policy explicitly
authorizes pre-creation. New active run directories must use
`_internal/inbox/runs/<run-id>/` or `_internal/outbox/runs/<run-id>/`, not bare
`session-<N>` paths.

`rank-repositories` and `plan --dry-run` fail closed when authority resolution
is missing, conflicting, unsupported by inspected documents, or based only on a
registry taxonomy claim.

## Task Packet

The packet is the executor-facing contract. It must include:
- task ID and title
- objective
- repository context snapshot
- authoritative sources
- allowed scope and denied actions
- allowed paths and denied paths when dispatching mutation
- validation requirements
- stop conditions
- human gate
- result-report path

Generated planning packets are drafts only until approved. Dispatch requires
the authority envelope and repository isolation required by
`agents/HERMES_AGENT_CONTRACT.md`.

## Result Report

The executor report is a claim. Minimum sections:
- starting repository state
- authoritative material consulted
- actions performed
- files changed
- commands run
- validation results
- warnings, errors, and scope deviations
- unresolved discrepancies
- evidence paths
- residual dirty state
- final claimed disposition
- next recommended decision

## Verification

Generated by:

```bash
python3 -m tools.hermes_orchestrator verify \
  --packet <packet.md> \
  --report <report.md> \
  --repo <path> \
  --allowed-path <path>
```

Verification compares packet/report existence, current changed paths, allowed
paths, and scope violations. Iteration 1 verifies structural scope. Iteration 2
must add deeper claim verification against validation output and evidence
artifacts before live dispatch is trusted.

Verified dispositions:
- `COMPLETED`
- `COMPLETED_WITH_WARNINGS`
- `SCOPE_VIOLATION`
- `INCOMPLETE`
- `AUTHORITY_VIOLATION`
- `HUMAN_DECISION_REQUIRED`

## Artifact Lifecycle Architecture Note

Hermes separates active workflow queues from durable task history.

Active queues are run-oriented:

- `_internal/inbox/runs/<run-id>/` receives task intent, draft packets, and
  human-dispatched work.
- `_internal/outbox/runs/<run-id>/` receives active result reports, validation
  output, proof files, and handoff artifacts for the current workflow.

Run IDs must be globally distinguishable inside Ivy Control VPS:

- `YYYY-MM-DD-<descriptive-slug>`
- `session-<N>-<descriptive-slug>`

Bare `_internal/inbox/session-<N>/` and `_internal/outbox/session-<N>/` paths
are legacy evidence locations only. New artifacts must not target them.

Durable validated history is repository-oriented and owned by
`schemas/hermes_orchestration/artifact-manifest.schema.json`:

```text
_internal/orchestration/repos/<repo>/tasks/<task-id>/
  manifest.json
  task-packet.md
  execution-report.md
  validation-report.<ext>
  execution-log.md

_internal/orchestration/cross-repo/tasks/<task-id>/
  manifest.json
  ...
```

Use the repository namespace when one managed repository owns the task. Use the
cross-repo namespace when a task spans multiple repositories or portfolio-level
coordination and should not be forced into one repository's history.

Task IDs are stable from packet creation through execution, validation,
archival, and later review. A task ID may appear in active inbox/outbox paths
and in exactly one durable archive namespace. Do not reuse a task ID for a
different task.

Archive promotion is explicit and copy-based. Hermes does not move or delete
active queue artifacts:

```bash
python3 -m tools.hermes_orchestrator archive-task \
  --task-id <task-id> \
  --repo <repo> \
  --packet _internal/inbox/runs/<run-id>/<packet>.md \
  --report _internal/outbox/runs/<run-id>/<report>.md \
  --validation _internal/outbox/runs/<run-id>/<validation>.json \
  --log _internal/logs/agents/YYYY-MM-DD/<task>.md
```

Repeat `--repo` for cross-repository tasks. `archive-task` only archives
validated work whose verification disposition is `COMPLETED` or
`COMPLETED_WITH_WARNINGS`. `HUMAN_DECISION_REQUIRED`, scope violations,
authority violations, incomplete work, missing artifacts, duplicate archive
roots, and invalid task IDs block archival.

Backward compatibility: existing `session-<N>` inbox/outbox paths remain valid
historical evidence locations and old links to them should not be rewritten
without a specific migration manifest. They are no longer valid destinations for
new work. The intentional change is that long-term Hermes task history should
be discovered from `_internal/orchestration/` manifests after validation rather
than by scanning historical session outboxes.

Before writing a new artifact path, validate it with:

```bash
python3 -m tools.hermes_orchestrator validate-artifact-destination --path <path>
```

Run state records:

## Supervised execution cycle and decision packets

The orchestration state, schemas, and tools are the canonical owner of this
cycle; Git publication remains exclusively governed by `docs/GIT_WORKFLOW.md`
and Git Steward. Hermes maximizes safely delegated work between GPT, Strong
Codex, and Buddy decision stages. It does not make the decision itself.

A supervised cycle is: `initialize → establish baseline → claim → provision
isolated worktree → dispatch maker → seal submission → run independent checker
→ pass | precise revision | stop/escalate → integrate or suspend → reconcile
clean state`. Each side-effecting transition is recorded before the effect.
Missing, stale, malformed, or contradictory evidence stops the run. Retries
retain the pinned base SHA, authority and acceptance digests, path manifest,
and budget; a maker can never approve its own submission.

`schemas/hermes_orchestration/decision-packet.schema.json` makes a decision
packet first-class. Its lifecycle is `identified → preparation_required →
preparation_in_progress → ready_for_review → under_review →
supplemental_evidence_required | decided | deferred → superseded | invalidated`.
Packets curate repository/runtime/semantic evidence, representative and
high-risk samples, counterexamples, uncertainties, options, tradeoffs,
recommendation, safe default, and a bounded response format. High-reasoning
review is tiered: deterministic evidence first; domain review second; only a
bounded unresolved semantic, architecture, policy, privacy, production,
credential, destructive, or capability-promotion question reaches GPT, Strong
Codex, or Buddy at the authority named in the packet.

## Runtime Diagnostic

Before a fresh Hermes test session, verify the runtime baseline:

```bash
python3 -m tools.hermes_orchestrator runtime-diagnostic \
  --backup ~/.hermes/memories/MEMORY.md.bak.stage1-20260728T090942Z
```

The diagnostic must report:
- canonical executable path `~/.local/bin/hermes`
- alternate compatibility wrapper `~/.hermes/hermes-agent/hermes`
- resolved venv executable target
- successful `--help` result for both entrypoints
- repository and live memory hashes
- memory drift status
- backup availability and restore command
- remaining entrypoint ambiguity

`status: PASS` is required before Stage 2 fresh-session tests.

## State Machine

| State | Entry | Exit artifact |
|---|---|---|
| ORIENT | Intent exists | repository context |
| ANALYZE | Context loaded | roadmap and eligibility views |
| AUTHOR | Task selected | task packet |
| DISPATCH | Authority and isolation proven | dispatch record |
| MONITOR | Dispatch recorded | result report location checked |
| VERIFY | Report exists | verification report |
| RESOLVE | Verification complete | disposition |
| UPDATE | Disposition known | continuity/journal proposal |
| SELECT_NEXT | Envelope remains | next eligibility decision |
| STOP | Gate, bound, blocker, or completion | final run state |

Every transition updates run-state before continuing.
